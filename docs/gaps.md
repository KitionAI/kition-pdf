# Gaps

> **Last updated:** 2026-11-27 · **Source:** `features.yaml` (updated 2026-11-27) and the engine's command list

Every known shortfall of Kition PDF, from the feature catalogue: features that are not yet `has`,
then the differences recorded on features that work. Update the feature in `features.yaml` when you
land work, then this list. The comparison with the target application is in
[parity/target-app-parity.md](parity/target-app-parity.md); the order of work is in [roadmap.md](roadmap.md).

## Differences on features that work

- `pdf.editor.keyboard-and-view` (P0, has): Measured in dev.html only (whether Kition Desktop gives the editor's frame the keyboard on open is not checked here). Select All takes every page up to 64 (the engine's text.select span) and the current page beyond. A mouse wheel's notch is told from a trackpad by its delta (whole 100 px or lines); real wheels and trackpads are not measured. Cmd+1 and Cmd+2 may be taken by a browser's own tab keys outside Kition.
- `pdf.editor.markup-and-comments` (P0, has): Comments are made from text selections, the find bar and the Comments panel (and a note from the page's menu): the tools that draw on the page are pdf.editor.annotation-tools; choosing, moving and resizing on the page is pdf.editor.annotation-select. A selection across pages makes one comment per page, each its own undo step (the engine has no batch of edits for the editor). Measured in dev.html only.
- `pdf.editor.params-and-fields` (P0, has): Points and rectangles are still typed: nothing is picked on the page (stage 10 of the plan). Lists of points of points (ink strokes) and objects (form values) are still JSON. Fields are filled in the panel and on the page (pdf.editor.forms-on-page). Measured in dev.html only.
- `pdf.editor.annotation-select` (P0, has): One comment at a time, on one page (no Shift-click to add one, no group drag). A drag moves a frame, not the comment's own pixels. Lines, arrows and polygons move but have no point handles (the engine's comment.edit has no vertex edit). The selected comment's colour, width and opacity are changed in the options bar (pdf.editor.annotation-tools) or its menu (colour). Form fields are filled on the page by pdf.editor.forms-on-page. Measured in dev.html only.
- `pdf.editor.annotation-tools` (P0, has): No callout, squiggly, insert or replace text, polygon, cloud, eraser, freehand highlight or stamp tool yet (comment.add has these types). The rail has no groups: every tool is its own button. The options bar has no fill colour or font size; a comment's own opacity and width show only once the editor set them this session (comment.list answers neither), and the tools' looks last for the session only. A new highlight does not open its note for typing. Measured in dev.html only; the tests insert Chinese text rather than going through a real input method.
- `pdf.editor.forms-on-page` (P0, has): The text of a field on a rotated page or with its own rotation (/MK /R) is typed level, not turned with it. No date picker, no formatting or validation feedback while typing (the engine formats and validates when the value is filled), no comb cells or password dots in the control (the page's appearance shows them once filled), no list-box multi-select with Shift-click beyond the browser's own, and a click on a selected radio button does not clear the group. Buttons and signature fields are the page's own (a click does nothing). The highlight setting lasts for the session. A face for Chinese comes from the host (the web editor adds Droid Sans Fallback): without one a Chinese value is still drawn as ?. Measured in dev.html only; the tests insert Chinese text rather than going through a real input method.
- `pdf.editor.links` (P1, has): A link goes to the top of its page at the current zoom: link.list answers the page only, not the destination's place and zoom. Only links go into the view history (bookmarks, thumbnails, find and the page field do not). Links to other files and scripts only say what they are. Measured in dev.html only (opening web addresses in Kition Desktop is not checked here).
- `pdf.editor.organize` (P0, has): No hover buttons on a thumbnail (the reference has them only in its page grid), no page grid (Organize mode), no thumbnail size, no Cmd+[ / Cmd+] to move the selection a place, no cut, copy and paste of pages, no files dropped between thumbnails, no Extract, Split or Replace in the menu (the web editor leaves out tools that write files). After a move or a delete the view goes to the top of the page that was current. A thumbnail's selection is the session's and goes with any change of the page count. Measured in dev.html only.
- `pdf.editor.bookmarks` (P1, has): A new bookmark goes to the top of the current page (the page in the middle of the view), not the place on it, and a bookmark goes to the top of its page: bookmark.add and bookmark.list carry no position or zoom. No drag to reorder and no current bookmark marked (as the reference); no Move up, Move down, Indent, Outdent, Set to current page, style, colour, cut, copy or paste in the menu (bookmark_move and bookmark_set_page exist), no search box, no Expand all. Only the bookmarks panel follows /PageMode (not thumbnails' own, attachments or layers; a document with comments does not open the Comments panel). A landscape page in Fit Width is not refitted page by page. The bookmark tools rest on the whole document for an agent's premises. Measured in dev.html only.
- `pdf.editor.repaint` (P1, has): A save rebases the document onto its new bytes and every page then counts as changed once: the thumbnails in view draw again (over their old pictures). The 1:1 page cache (100 % at device pixel ratio 1, and every view below it) still empties on any edit, so those views draw their visible pages again (test:cache holds it to that). The page canvas repaints its whole view after an edit, from kept tiles where it can: the SDK's run takes the damaged area before the command runs, and the editor does not name it. 128 MiB of tiles are kept (about three pages at 200 % Fit Width), so a long scroll back draws pages again. Scrolling into pages not yet drawn still waits for them (the SDK holds the view until its frame lands). Measured in dev.html only.
- `pdf.editor.reading` (P1, has): A press that starts selecting text still closes the find bar (test:selection holds it to that; a click in a margin or off the pages keeps it). The find bar opens empty, as the reference's does: an earlier query comes back with Up. Four quick clicks do not select the page (the canvas counts one to three, then starts again). No single page, two-page or two-page scrolling layout and no view rotation: the page layout is the engine binding's one column, and every page-local coordinate (selection, comments, fields, links) is the page as the file turns it. Focus on its own keeps the view; only Full screen fits the page. Whole words only treats Chinese and Japanese characters as letters. No search results panel. Measured in dev.html only (Kition Desktop's frame and full screen are not checked here).
